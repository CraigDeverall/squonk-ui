# Foundations

SquonkUI is a small set of decisions applied the same way everywhere: one
type family, one spacing scale, a handful of named shapes and colours, and
components that already behave correctly for keyboards, screen readers and
narrow screens. These pages show those decisions with the real components, in
the theme you are viewing.

## Principles

- **Calm and readable.** Clear hierarchy, generous but deliberate space, one leading
  action per task, and emphasis used sparingly.
- **Named decisions, not numbers.** Components read purpose tokens such as "the gap
  between a field's label and its input", so a theme changes what a purpose means
  in one place. See [Purpose tokens](?path=/docs/foundations-purpose-tokens--docs).
- **Accessible by construction.** Behaviour comes from React Aria: labels, focus,
  keyboard and announcements are built in. Your content still has to be clear.
- **Every state counts.** Empty, loading, error, long-text and phone-width states
  get the same care as the populated desktop screen.

## How the pieces fit

| Layer | What it is | Use it to |
| --- | --- | --- |
| Layout primitives | `VStack`, `HStack`, `Cluster`, `Grid`, `Split`, `Container`… | Arrange components; the parent owns placement and spacing |
| Named layouts | `Page`, `Section`, `Card`, `Header`, `Sidebar` | Give common screens a consistent shape |
| Components | Buttons, fields, overlays, tables… | Do the work, with behaviour and accessibility built in |
| Presentation | `compact`, `default`, `large`, `hero` registers | Size a region's controls for its job, from dense admin to marketing |
| Theme | `SquonkThemeProvider`, `ThemeModifier`, `ThemeStyleBlock` | Change primitives, purposes, mode or density for an app or a subtree |

## What the library promises, and what your app checks

The library ships tested components: keyboard and focus behaviour, light and dark
contrast for its own text roles, visual baselines and React Aria semantics. Your
app is responsible for its content and composition: meaningful labels and
headings, the contrast of any custom colours or images, sensible focus order
across the screen, and testing with real data at real widths.

## Before adding something new

Start from the user's need and compare it with what exists: a composition of
existing components, a scoped theme change or a new purpose token is usually the
right answer. A new public component needs use and avoid criteria, its states,
keyboard and focus behaviour, responsive behaviour, the tokens it binds to, a live
example and tests. When several teams ask for similar changes, prefer one shared
extension over several local ones.
